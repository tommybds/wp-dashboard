Plan de refonte · dashboard.sumoto.fr · septembre 2026

Refonte graphique et ergonomique du dashboard Parc WordPress

Une console d'exploitation sobre, lisible sur grand écran et correcte au téléphone, construite sans chaîne de build : HTML, CSS et modules ES servis tels quels par nginx. Cinq phases, chacune livrable et déployable seule, sans jamais casser l'outil qui sert tous les jours.

Stack vanilla modulaire, zéro build Direction console d'exploitation Cibles bureau d'abord, mobile correct Effort estimé 14 à 18 jours

Réalisé — 3 septembre 2026

Les cinq phases sont livrées et déployées. Le plan ci-dessous est conservé tel qu'il a été écrit : il dit ce qui était prévu, pas ce qui existe. Pour l'état actuel du front, voir la section Frontend du README et docs/captures/.

  1. ✔ Phase 1 — Fondations : jetons, polices locales, sprite d'icônes, coque, découpage en modules ES, script de déploiement.
  2. ✔ Phase 2 — Parc et page site : file « à traiter », liste filtrable, page site à cinq onglets, recherche ⌘K, actions groupées.
  3. ✔ Phase 3 — Incidents, Sécurité, Changements : écran Incidents, pages à ancres, chronologie unifiée ; plus un seul sous-onglet.
  4. ✔ Phase 4 — Gestion et Réglages : serveurs en formulaires (validation champ par champ), Réglages devenu une page.
  5. ✔ Phase 5 — Mobile et finition : barre d'onglets basse, liste de cartes, feuille d'actions, passe d'accessibilité (tools/check_a11y.py), retrait du code mort (tools/check_dead.py), README et captures.

1. État des lieux

Le dashboard a été construit en trois jours, fonctionnalité par fonctionnalité. Il rend service, mais sa forme est celle d'une accumulation : chaque écran a été ajouté là où il y avait de la place, avec la charte qu'il avait sous la main.

MesureValeurCe que ça dit
Fichier unique index.html3 750 lignesTout le front dans un fichier : impossible à relire par écran, conflits à chaque modification
JavaScript inline3 081 lignes · 197 fonctionsAucun découpage par responsabilité, état global partagé (FLEET, CUR, SEL, FILT…)
Accès au DOM par identifiant324Chaque écran est couplé à des ids uniques ; déplacer une section casse son chargeur (déjà arrivé)
Rendu par innerHTML =193Le HTML est produit dans des chaînes JS : pas de composant réutilisable, échappement à la main

Boutons102Actions présentées à plat, sans hiérarchie de fréquence ni de risque
Modales7Plus un tiroir, plus une barre de notifications : trois couches qui se superposent
Jetons CSS29Une échelle existe (polices, rayons, espacements) mais l'iconographie est en emoji et la couleur d'état se confond avec l'accent

Ce qui gêne à l'usage

A
Le tiroir porte toute la fiche site.

Indicateurs, actions, extensions, restauration, VizProof, sauvegardes, historique : une colonne de 500 px qui défile sur trois écrans. La fiche d'un site est l'écran le plus utilisé, il mérite une vraie page.

B
La page d'accueil ne dit pas quoi faire.

Six tuiles, puis un tableau de 20 lignes trié par nom. Ce qui demande une action (site down, PHP en fin de vie, vulnérabilité critique, sauvegarde en retard) n'est pas remonté en tête.

C
Trois vocabulaires d'état.

Pastille de couleur, texte coloré, chip : « 7.0.4 → 7.1 » en orange, « v1.0.3 · à mettre à jour » en jaune, « il y a 15 h » en vert. Le lecteur doit ré-apprendre le code par colonne.

D
Les emoji font office d'icônes.

🕘 🌓 ⚙️ ⏻ 🛡 ↻ ＋ : rendu différent selon l'OS, taille non maîtrisée, aucun état survol ou désactivé. C'est le premier signal « bricolé » de l'interface.

E
Sécurité et Historique sont des tiroirs de rangement.

Huit sous-onglets pour la sécurité, deux pour l'historique, alors que l'utilisateur pose trois questions : qu'est-ce qui est cassé, qu'est-ce qui est exposé, qu'est-ce qui a changé.

F
Mobile : lisible, pas utilisable.

Le tableau défile horizontalement, le tiroir prend l'écran, les actions à confirmation en deux clics sont fines. On peut consulter, pas agir.

2. Principes de la refonte

  1. Une console, pas un site. Densité maîtrisée, typographie nette, pas de hero, pas d'illustration. La couleur est réservée aux états ; l'accent sert à l'action principale et au focus, rien d'autre.
  2. Ce qui demande une action arrive en premier. Chaque écran s'ouvre sur sa file d'attente : incidents, puis mises à jour, puis le reste.
  3. Un seul langage d'état. Quatre niveaux (ok, attention, critique, inconnu), une seule forme (chip avec point), les mêmes mots partout.
  4. Le site est une page, pas un tiroir. Adresse partageable, onglets, historique complet, actions groupées par intention.
  5. Le risque se lit avant de cliquer. Les actions qui modifient un site sont visuellement distinctes de celles qui lisent, et la confirmation dit ce qui va se passer.
  6. Rien ne bloque. Tout ce qui dure plus de deux secondes tourne en tâche de fond, visible dans la barre de progression, reprenable après rechargement.
  7. Zéro build. Le code déployé est le code écrit : modules ES natifs, CSS natif, un fichier de version pour le cache.

3. Design system

Couleur

Neutres froids à légère dominante bleue, deux fonds (page et surface), un accent unique pour l'action et le focus, et une gamme d'état indépendante de l'accent. Le thème sombre est dessiné, pas inversé : les fonds d'état y sont assombris, les textes d'état éclaircis.

Page#F2F4F7 · sombre #0F1418
Surface#FFFFFF · sombre #161C22
Encre#18232D · sombre #E7ECF1
Accent#1F5FA3 · sombre #6FA8DE
OK#1E7F5C · sombre #5CC29A
Attention#9A6A0B · sombre #E0B24C
Critique#B23B36 · sombre #EF8580

Règle de contraste : texte courant ≥ 7:1, texte secondaire ≥ 4.5:1, chips ≥ 4.5:1 sur leur fond, dans les deux thèmes. Vérifié par script à chaque modification des jetons (voir §8).

Typographie

RôleFaceUsage
Titres et navigationArchivo 600Nom de site, titres d'écran, onglets. Semi-condensée : gagne de la place dans les en-têtes sans perdre en lisibilité
Texte et interfaceIBM Plex Sans 400 / 500Tout le reste. Chiffres en tabular-nums dans les colonnes
Données et codeIBM Plex Mono 400Versions, chemins, identifiants, sorties wp-cli, labels de colonnes en capitales espacées

Échelle : 12 / 13 / 14 / 16 / 20 / 26 px. Le corps de l'interface est à 14 px (13 en mode compact), le corps des textes explicatifs à 16. Les polices sont servies localement depuis public/fonts/ (pas d'appel à Google Fonts depuis une console d'administration).

Espace, formes, élévation

  • Espacements sur une base de 4 : 4, 8, 12, 16, 24, 32, 48.
  • Rayons : 4 px pour les contrôles, 6 px pour les surfaces, pilule pour les chips. Pas d'arrondi généreux.
  • Élévation par bordure, pas par ombre : la seule ombre est celle des couches flottantes (menu, panneau latéral, notification).
  • Une surface n'est une carte que si elle est manipulable seule (un site dans la liste mobile, un job en cours). Les groupes de valeurs sont des listes label/valeur, pas des cartes.

Iconographie

Un sprite SVG unique de 24 icônes à trait de 1,5 px (Lucide, licence ISC), 16 px dans les lignes, 20 px dans les barres. Remplace tous les emoji. Chaque icône d'action est accompagnée d'un libellé ou d'un aria-label ; aucune icône seule dans une colonne de tableau.

Langage d'état

● à jour

Rien à faire. Vert réservé à cet état, jamais aux valeurs neutres comme un délai.

● 4 MAJ

Action recommandée, sans urgence : mises à jour disponibles, sauvegarde de plus de 48 h, PHP en fin de support.

● down

Action requise : site injoignable, vulnérabilité critique corrigeable, checksums modifiés, admin inconnu.

○ inconnu

Donnée absente ou périmée (serveur injoignable, agent muet). Gris, jamais vert par défaut.

4. Architecture d'écrans

Quatre onglets et vingt-cinq sections deviennent cinq destinations dans une barre latérale, plus une page par site. Les sous-onglets disparaissent : chaque destination est une seule page qui commence par ce qui demande une action.

DestinationQuestion à laquelle elle répondCe qu'elle absorbe de l'existant
ParcOù en est le parc, qu'est-ce qui attend ?Tableau de bord, tuiles, filtres, vues, export, actions groupées
IncidentsQu'est-ce qui est cassé ou périmé maintenant ?Sites down (Kuma), erreurs PHP fatales, serveurs injoignables, checksums modifiés, certificats < 21 j
SécuritéQu'est-ce qui est exposé ?Vulnérabilités (par site / par extension), administrateurs et référence, plugins à risque, PHP obsolète
ChangementsQu'est-ce qui a bougé, et qui l'a fait ?Historique des changements, journal des actions, événements des agents, tendance
GestionComment le parc est-il branché ?Installs découverts, sites REST, moniteurs Kuma, serveurs, docroots, clés SSH, appairage d'agent
Site #site/elwave.frTout sur ce site, et agir dessusLe tiroir entier, devenu une page à cinq onglets

La page site

En-tête : nom, client, serveur, état Kuma, chemin, dernier relevé, et une action principale déterminée par l'état (« MAJ sûre — 4 ext. » s'il y a des mises à jour, « Re-scan » sinon). Le reste des actions vit dans un menu « Actions » groupé par intention : mettre à jour, vérifier, sauvegarder, connecter. Cinq onglets : Vue d'ensemble, Extensions, Sécurité, Sauvegardes et restauration, Historique.

Mobile

Sous 720 px : la barre latérale devient une barre d'onglets en bas (Parc, Incidents, Sécurité, Plus), la liste des sites devient une liste de cartes (nom, état, deux chiffres), la page site garde ses onglets en défilement horizontal, et les actions passent dans une feuille qui monte du bas avec confirmation par bouton plein largeur. Les tableaux larges restent défilables mais ne sont plus le seul moyen de lire.

5. Composants clés

Chip d'état

Point + libellé, quatre niveaux, une seule classe. Remplace les textes colorés des colonnes WordPress, Extensions, Backup, Vizproof.

Ligne de site

Un composant pour le tableau bureau et la carte mobile, alimenté par le même objet. Clic = page site ; les cases à cocher restent pour le groupé.

Menu d'actions

Groupes « Mettre à jour / Vérifier / Sauvegarder / Connecter », les actions qui modifient marquées d'un trait d'attention, désactivées avec la raison en infobulle (site REST, extension gelée, job en cours).

Confirmation

Une seule modale pour tout : titre = l'action, corps = ce qui va se passer (site, cible, garde-fous actifs, base de données touchée ou non), bouton = le verbe.

Suivi de job

Le même composant dans la barre de progression, dans la page site et dans la modale groupée : étapes, état, durée, verdict, lien rapport. Reprend la barre livrée le 2 septembre.

Recherche globale ⌘K

Sites, extensions (à jour ou non), administrateurs, actions (« collecter », « réglages »). Remplace le champ de filtre comme point d'entrée principal.

Tableau

En-tête collant, tri par colonne avec aria-sort, colonnes masquables et mémorisées, chiffres tabulaires, densité normale / compacte.

Courbe de tendance

Aire + ligne + point final, grille faible, axe lisible, couleurs par jetons. Reprend le composant existant, sans changement de comportement.

6. Architecture du code

Le principe : découper sans outil. Les navigateurs chargent des modules ES nativement, nginx sert des fichiers ; il n'y a rien à compiler.

public/
  index.html            coque : <nav>, <main>, <div id="jobs">, un seul <script type="module" src="app.js?v=…">
  app.js                démarrage, routeur par fragment, chargement de la flotte
  version.js            export const V = "2026-09-12-1" ; suffixe ?v= posé par un script de déploiement
  css/
    tokens.css          jetons (couleur × 2 thèmes, type, espace, rayons, élévation)
    base.css            reset, typographie, focus, reduced-motion
    components.css      chip, bouton, tableau, menu, modale, feuille mobile, job
    screens.css         mises en page des six écrans
  lib/
    api.js              fetch, session, X-Dash, gestion 401, erreurs typées
    state.js            flotte, sélection, filtres ; abonnements (EventTarget)
    poll.js             sondage borné (existant)
    dom.js              h(), esc(), mount(), délégation
    format.js           dates relatives, versions, tailles, pluriels
    icons.js            sprite SVG inliné une fois
  components/
    chip.js  actions-menu.js  confirm.js  job.js  table.js  search.js  toast.js  sheet.js
  screens/
    parc.js  incidents.js  securite.js  changements.js  gestion.js  site.js  reglages.js
  fonts/                Archivo, IBM Plex Sans, IBM Plex Mono (woff2)
  • Rendu : une petite fonction h(tag, attrs, children) qui construit du DOM (pas de chaînes HTML), donc plus d'échappement à la main ; les 193 innerHTML disparaissent avec les écrans qu'ils rendaient.
  • État : un module state.js qui détient la flotte et émet des événements ; les écrans s'y abonnent et se rerendent seuls. Fin des variables globales partagées.
  • Routage : #parc, #incidents, #site/elwave.fr/extensions… même mécanisme qu'aujourd'hui, avec un vrai historique (déjà en place).
  • Cache : nginx garde no-store sur l'API et index.html, mais peut mettre en cache css/, lib/, components/, screens/ un an grâce au ?v= ; la page se charge plus vite et le déploiement reste un scp.
  • Backend : inchangé. Les 51 routes existantes suffisent ; deux ajouts seulement, listés en §9.

7. Phases

Chaque phase se termine par un déploiement en production. L'ancien écran reste disponible tant que le nouveau n'a pas remplacé exactement ses fonctions : la migration se fait écran par écran, pas en bascule unique.

Phase 1 — Fondations

3 jours
  • Jetons et CSS de base (deux thèmes), polices locales, sprite d'icônes, chip d'état, boutons, tableau.
  • Coque : barre latérale, en-tête d'écran, zone de jobs. Les écrans existants sont montés dedans tels quels, chargés à la demande.
  • Découpage mécanique du fichier unique en modules, sans changer le comportement : lib/, components/poll.js, components/job.js, écrans dans screens/.
  • Script de déploiement qui pose le ?v= et la règle de cache nginx.
Livré quand : tous les écrans actuels fonctionnent dans la nouvelle coque, avec les nouveaux jetons et sans emoji ; zéro erreur console ; les 21 routes GET sondées après déploiement ; la page se charge en moins de 300 ms hors fleet.json.

Phase 2 — Parc et page site

4 à 5 jours
  • Écran Parc : file « à traiter » (règles explicites : down, CVE critique corrigeable, sauvegarde > 48 h, serveur injoignable, admin inconnu), liste des sites avec chips, colonnes masquables, vues sauvegardées reprises.
  • Page site à cinq onglets, action principale déduite de l'état, menu d'actions groupé, confirmation unique. Le tiroir est retiré.
  • Recherche globale ⌘K.
  • Actions groupées reprises dans une barre contextuelle en bas de liste, avec le composant job.
Livré quand : chaque bouton du tiroir actuel a son équivalent dans la page site (vérifié par le croisement data-act ↔ ACTIONS déjà scripté) ; MAJ sûre, retour arrière, gel, connexion VizProof testés sur elwave.fr.

Phase 3 — Incidents, Sécurité, Changements

3 à 4 jours
  • Incidents : nouvel écran, agrégat des sources existantes, tri par gravité puis ancienneté, action en ligne.
  • Sécurité : vulnérabilités par site / par extension (reprise), administrateurs et référence, plugins à risque, PHP obsolète, dans une seule page à ancres.
  • Changements : historique, journal, événements agents et tendance fusionnés dans une chronologie filtrable par site, type et gravité.
Livré quand : les 8 sous-onglets Sécurité et les 2 d'Historique n'existent plus et rien de ce qu'ils montraient n'a disparu (liste de contrôle par section) ; les pastilles de compteur de la barre latérale correspondent aux règles de la file « à traiter ».

Phase 4 — Gestion et Réglages

2 jours
  • Gestion : installs découverts, sites REST, moniteurs, serveurs, docroots, clés SSH, agent — en formulaires structurés à la place de l'éditeur JSON (validation côté serveur déjà en place).
  • Réglages : une page au lieu d'une modale ; sections cadence, alertes, VizProof, contrôle visuel, clés.
Livré quand : un serveur peut être ajouté sans toucher au JSON ; un refus de validation s'affiche champ par champ.

Phase 5 — Mobile et finition

2 à 3 jours
  • Barre d'onglets basse, liste de cartes, feuille d'actions, page site en défilement d'onglets.
  • Passe d'accessibilité : navigation clavier complète, focus visible, rôles, contrastes vérifiés, prefers-reduced-motion.
  • Suppression de l'ancien code, README et captures à jour.
Livré quand : à 390 px, on peut lire l'état du parc, ouvrir un incident, lancer un re-scan et une MAJ sûre sans zoom ni défilement horizontal ; rapport d'accessibilité sans critique.

8. Vérification

  • Page bouchonnée : la méthode déjà utilisée (index servi localement, fetch remplacé par des fixtures réelles) devient un script versionné, tools/preview.py, avec des scénarios (job lent, serveur stale, anomalie visuelle, 0 site, 200 sites).
  • Contrôles automatiques à chaque phase : node --check sur chaque module, contraste des jetons calculé par script (seuils du §3), croisement des appels d'API avec les routes du backend, croisement des actions avec ACTIONS, absence d'innerHTML sur des données distantes.
  • Parcours réels : sur elwave.fr, à chaque phase qui touche une action : re-scan, MAJ unitaire sous contrôle visuel, MAJ sûre en simulation, gel et rétablissement.
  • Revue visuelle : deux thèmes × trois largeurs (1440, 1024, 390) sur les six écrans, captures archivées dans le dépôt pour comparer d'une phase à l'autre.

9. Risques et décisions

Le dashboard est en production et sert à intervenir sur des sites clients. Aucune phase ne doit laisser une action sans équivalent, même une journée. C'est la contrainte qui impose la migration écran par écran plutôt qu'une réécriture parallèle.

Risques

  • Régression silencieuse d'une action : couverte par le croisement automatique actions ↔ backend et par les parcours réels sur elwave.
  • Dérive du design system pendant le chantier : les jetons sont figés en phase 1 ; toute nouvelle valeur passe par une modification de tokens.css, jamais par un style en ligne (contrôle par script).
  • Cache navigateur après déploiement : le ?v= le règle pour les modules ; index.html reste no-store.
  • Polices locales : trois familles en woff2, environ 180 Ko, chargées avec font-display: swap et un repli système déclaré.

Décisions à prendre avant la phase 1

  1. Règles de la file « à traiter » : la liste proposée en phase 2 est un point de départ ; à valider, car elle pilote aussi les compteurs de la barre latérale et, plus tard, les alertes.
  2. Nom et logo : « Parc WordPress » reste-t-il le nom, ou le dashboard prend-il une identité Sumotori (favicon, marque dans la barre latérale) ? Le style choisi n'en dépend pas, le libellé si.
  3. Deux ajouts backend à confirmer : une route GET /api/incidents qui agrège les sources (sinon l'écran Incidents recalcule côté client, ce qui marche mais coûte cinq requêtes), et un champ columns dans les vues sauvegardées.
  4. Ordre des phases 3 et 4 : interchangeables ; la 3 apporte plus à l'usage quotidien, la 4 ferme plus vite l'éditeur JSON.
